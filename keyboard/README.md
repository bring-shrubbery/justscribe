# JustScribe Keyboard (iOS)

A standard keyboard for iPhone and iPad with dictation built in, in the spirit of Wispr Flow's
mobile app: type as usual, tap the microphone to talk, and the text appears in whatever app you
are typing in. Transcription runs on the device.

Status: a prototype, on the `keyboard` branch. It builds, its tests pass and the app launches
in the simulator. The dictation flow has not been run end to end yet: that needs a real device
(see [What is verified](#what-is-verified)).

```bash
cd keyboard
xcodegen                     # regenerate JustScribeKeyboard.xcodeproj after editing project.yml
xcodebuild -project JustScribeKeyboard.xcodeproj -scheme JustScribe \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' test
```

## Testing the keyboard in the simulator

`UITests/KeyboardTypingUITests` types on the keyboard with real touches. It needs a simulator
with the JustScribe keyboard enabled and selected, which can be set without Settings:

```bash
xcrun simctl spawn $SIM defaults write -g AppleKeyboards -array \
  "com.quassum.justscribe.keyboard" "en_US@sw=QWERTY;hw=Automatic" "emoji@sw=Emoji"
xcrun simctl spawn $SIM defaults write com.apple.keyboard.preferences KeyboardLastUsed \
  -string "com.quassum.justscribe.keyboard"
xcrun simctl shutdown $SIM && xcrun simctl boot $SIM
```

Debug builds launched with `-keyboardLab YES` open a bare text field with the keyboard up, for
screenshots (`xcrun simctl io $SIM screenshot`). Check the keys in an optimized build too
(`-configuration Release`): a statically linked package resolves resources differently there,
and one such difference once drew every key invisible.

## TestFlight

Every push to `main` or `keyboard` that touches `keyboard/` (and any manual run of the
**iOS TestFlight** workflow) builds Release and uploads it to TestFlight:
`.github/workflows/testflight.yml` on GitHub's macOS runners, then `fastlane beta`
(`fastlane/Fastfile`). It never runs on a self-hosted runner, because this repository is public.

- **App Store Connect**: the iOS platform of the existing **JustScribe** app (6758214206),
  so the Mac and iOS apps are one listing. Bundle IDs `com.quassum.justscribe` (app) and
  `com.quassum.justscribe.keyboard`, both in App Group `group.com.quassum.justscribe`.
- **Build number**: the latest iOS TestFlight build + 1. **Version**: `MARKETING_VERSION`
  in `project.yml`.
- **Signing**: manual, from the Apple Distribution certificate "JustScribe iOS CI"
  (`7RW7K7J34G`, expires 2027-10-22). Its identity goes into a throwaway keychain, and App
  Store profiles for both bundle IDs are fetched or created through the API on each run.
- **Secrets**: `ASC_API_KEY_ID`, `ASC_API_ISSUER_ID` and `ASC_API_KEY_P8` (shared with the Mac
  release), plus `IOS_DISTRIBUTION_P12` (base64 `.p12`) and `IOS_DISTRIBUTION_P12_PASSWORD`.
  When the certificate expires, create a new one (`asc certificates create --certificate-type
  DISTRIBUTION --generate-csr …`), update `CERTIFICATE_ID` in the Fastfile, and replace those
  two secrets.

From a Mac: `cd keyboard && bundle exec fastlane beta`, with `ASC_API_KEY_PATH` and
`IOS_DISTRIBUTION_P12_PATH` pointing to the files instead of the base64 secrets.

## Layout

| Folder          | What                                                                                  |
| --------------- | ------------------------------------------------------------------------------------- |
| `JustScribe/`   | The host app: set-up steps, the dictation session (microphone + speech), Try It field |
| `Keyboard/`     | The keyboard extension: keys, suggestions, emoji, microphone and recording bar         |
| `Shared/`       | Compiled into both: `DictationBridge` (App Group + Darwin notifications), accent color |
| `KeyboardCore/` | The keyboard engine as a local Swift package (layouts, keys, callouts, gestures)      |
| `Tests/`        | Unit tests (Swift Testing), hosted in the app                                          |

The project is generated by XcodeGen from `project.yml`; sources are synchronized folders, so new
files are picked up without regenerating.

## How dictation works

iOS gives keyboard extensions no microphone, and limits them to roughly 60–70 MB of memory, so
no speech model can run in one. The app does the recording and the keyboard drives it, the same
way Wispr Flow does:

1. The user taps the microphone on the keyboard. With no live session, the keyboard opens
   `justscribe://dictate` (through the responder chain: `UrlOpener` in KeyboardCore).
2. The app opens, starts its audio session and microphone, and starts recording at once. It shows
   "Go back to the app you were typing in": the user taps ◀ in the status bar. There is no public
   API to switch back for them.
3. The app keeps running in the background, recording, because of the `audio` background mode.
   The orange dot shows. The keyboard (re-created when the user came back) reads the session's
   phase from the App Group and shows the recording bar: cancel, level, timer, done.
4. Done sends a Darwin notification; the app finishes the transcription, writes the text to the
   App Group and posts back; the keyboard inserts it once (`DictationBridge.pendingResult`), with
   a space before it when needed (`TextSpacing`).
5. The session stays live for a few minutes (`Stays ready for`, default 5) with the microphone
   open, so later dictations start straight from the keyboard with no app switch. After that the
   app closes the microphone and the next tap opens the app again.

The keyboard needs **Full Access** for the App Group; without it the microphone explains what to
turn on. Nothing leaves the phone either way.

Transcription is Apple's `SpeechAnalyzer` (`SpeechTranscriber`, or `DictationTranscriber` where
that is unavailable): no model ships in the app, iOS downloads the language. Audio is fed while
the user speaks, so the text is nearly ready when they stop.

## Feasibility

**It is feasible.** Every part of the flow uses mechanisms other dictation keyboards ship with
on the App Store today. The trade-offs come from iOS, not from this code:

- **One app switch per session.** The first dictation after a while always goes through the app
  and back. This is the main friction, and it is unavoidable: Wispr Flow has it too. A longer
  "stays ready" time reduces it, at the cost of the microphone indicator staying on.
- **Opening the app from the keyboard is not public API.** The responder-chain call works on
  iOS 26/27 and keyboards that do it pass review, but Apple could break it in any release.
- **App Review.** Background audio used to keep a microphone open, and Full Access, both draw
  questions. We need a clear privacy explanation (all on device) and a demo video for review.
- **Models run in the app, never in the keyboard.** Parakeet (FluidAudio) or Whisper (WhisperKit),
  as on the Mac, can replace `SpeechAnalyzer` behind `TranscriptionRun`. Core ML may use the Neural
  Engine and CPU in the background, not the GPU. That suits Parakeet; Whisper needs to be measured.
- **Clean-up.** Apple's Foundation Models also exist on iOS 26, so the Mac's default clean-up
  backend should carry over. The hosted backends carry over too; the CLI agents do not.

### KeyboardKit

`KeyboardCore/` is the source of KeyboardKit **9.9.1**, the last MIT-licensed release. From 10.0
onward KeyboardKit is closed source under a commercial license, so newer versions cannot be used
this way.

- Its `LICENSE` (MIT, Daniel Saidi) **must stay** with the code: the MIT license requires the
  copyright and permission notice in every copy. Everything else that credited or advertised it is
  gone: file headers, the icon, the `KeyboardKit Pro` placeholders, the license gate, the
  license-registration screens, themes, docs and links. Identifiers and settings keys are renamed.
- The free 9.x code left out what KeyboardKit Pro sold, and those features are simply missing
  rather than unlocked. Here they are, with what replaces them:

  | Missing from the free code               | Here                                               |
  | ---------------------------------------- | -------------------------------------------------- |
  | Autocomplete                             | `TextCheckerAutocompleteService` (`UITextChecker`) |
  | Emoji keyboard                           | `EmojiKeyboard`, a basic grid over the emoji data  |
  | Dictation                                | The app session above                              |
  | Layouts and callouts for other languages | Not yet: English QWERTY only                       |
  | Next-word prediction, learning words     | Not yet                                            |
  | Themes, full-document context            | Not needed                                         |

## Not done yet

- Other languages: layouts (AZERTY, QWERTZ, …), callouts and a language switcher.
- Better suggestions: next-word prediction, learned words, contacts (`UILexicon`).
- Emoji search, recents, skin tones.
- Sharing the Mac's dictation pipeline (vocabulary, voice commands, modes, clean-up): today it
  lives in the Mac app target and would need to move to a shared package first.
- An app icon, onboarding that checks the keyboard is actually enabled, and a
  "Back to <app>" hint that knows the app's name (iOS no longer tells keyboards who hosts them).

## What is verified

- KeyboardCore, the app and the keyboard build for the iOS 27.1 simulator with no warnings in the
  new code.
- The unit tests pass: the bridge (heartbeat, a result inserted once, stale results ignored) and
  the spacing rules.
- The app launches in the simulator and shows its set-up screen.

Not verified, and to check on a device:

- The keyboard on screen: enabling it means going through Settings, which could not be automated
  here.
- Speech: in the simulator, on-device speech reports "no audio format for this language". The
  simulator does not install speech assets, so this needs a device.
- The whole round trip: opening the app from the keyboard, recording in the background, and
  inserting the result.
